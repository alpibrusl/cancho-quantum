Can a compiler refuse to clone a qubit?

A quantum simulator written in cancho: {{N_GATES}} gates, noise (sampled and exact), OpenQASM input, and a type checker that refuses to clone, drop or reuse a qubit. Built to find out what a language with linear types catches in quantum code, and to say plainly what it misses.

What the type checker found

  
The idea: qubits are linear resources. The test: write the simulator, then try to write the mistakes, and see which ones the checker stops. No compiler change was made.

  

    
No-cloning is a type error
A Qubit is a res: it cannot be copied, cannot be dropped, and only measure ends it. Cloning, dropping, measuring twice and escaping a borrow are all refused by rules cancho already had.

    
Reproducible to the byte
{{N_GOLDEN}} circuits. Each runs six ways (interpreted and compiled; Cranelift and LLVM; aarch64 under emulation), three for the {{N_DM}} density-matrix circuits, which are interpreted only. The outputs are identical, and their hashes are checked in. Adding noise, QASM and the density matrix did not change one earlier hash.

    
Gaps, stated up front
A repeated qubit in a multi-qubit gate (CNOT, SWAP, Toffoli with one qubit twice) is not refused at check time: it is accepted and stops at run time. A Qubit can also be written by hand from any module. The gallery lists both, and what would close them.

For humans

  
What this is, what you can do with it today, and how far to trust it.

  

    
What you can do

      
    
        
  • Run a circuit: a few lines (h 0, cx 0 1, rz 2 1 4) and read the amplitudes, or draw outcomes with sample 1000.
    • 
        
  • Add noise (depol 1 1 4, readout 1 20, or a model for every gate) and either sample it or ask for the exact density matrix (dm 2).
    • 
        
  • Feed it OpenQASM 2.0 from Qiskit, or the algorithms in tests/diff/.
    • 
        
  • Write a typed program with Qubit values and see the checker say no when you clone one.
    • 
        
  • Check the numbers yourself against Qiskit, and the bytes against the checked-in hashes.
    • 
      

    
How far to trust it

      
    
        
  • Amplitudes and density matrices match Qiskit 2.6.1 to {{WORST}} on {{N_CIRCUITS}} circuits (the gate is 1e-12). Up to 20 qubits (10 for the density matrix).
    • 
        
  • Sampled noise is checked as an average: thousands of runs against the exact density matrix, not run by run.
    • 
        
  • It is a research prototype: one reference implementation, one compiler revision, one machine plus emulation.
    • 
        
  • It is not fast and not a rival to Qiskit Aer or qsim, and does not try to be.
    • 
      

  

  
The input is plain text, one operation per line, so a circuit can be hashed and kept beside its reference output. Sampled noise and sampling:


n 3        # three qubits
h 0
cx 0 1     # a Bell pair
depol 1 1 4  # depolarizing noise on qubit 1, probability 1/4
model2 1 50  # or: noise after every two-qubit gate from here on
ry 2 1 3   # rotate qubit 2 by pi/3
seed 7     # the sampler is seeded: same seed, same bits
readout 1 20 # report each measured bit flipped, 1 time in 20
coher 0 50000 70000  # qubit 0: T1 50 us, T2 70 us (nanoseconds)
wait 0 20000  # ...and it idles for 20 us, so it decays
sample 1000  # 1000 outcomes, counted per bit string
m 0        # or measure qubit 0 and collapse the state

  
The same noise, exactly (dm in place of n, up to 10 qubits): one run prints the density matrix, and purity, trace and probs ask for its properties.


dm 2
h 0
cx 0 1
depol 1 1 4
purity     # prints purity 0.5833...

What not to get wrong

      
    
        
  • Do not fix a refusal by copying a qubit. It cannot be copied; qubit.measure ends it.
    • 
        
  • CNOT on one qubit twice compiles. It is a known gap, not a bug in your setup; do not report it as a refusal.
    • 
        
  • Qubit { ... } can be written by hand from any module. That is a known gap too.
    • 
        
  • Do not edit tests/golden/ to make a check pass.
    • 
        
  • The aarch64 result is emulation, not hardware.
    •

The newer parts, timed

  
Typed from docs/benchmark.md (one machine, minimum of 5 whole-process runs, start-up of about 1.2 ms included), not rebuilt by this page.

  

    
Reading OpenQASM
A 300-gate circuit takes 1.9 ms with multiples of pi, 2.3 ms with decimal angles and 2.9 ms with every gate a call of a definition; Qiskit’s reader alone takes 1 to 1.7 ms. One call of a defined gate costs 1.2 to 1.7 microseconds; 100,000 calls take 0.21 s against 0.047 s written out. The budget of 200,000 calls is refused in 78 ms.

    
A known slow spot
A QASM run prints every non-zero amplitude, about 17 microseconds each: a dense 14-qubit state takes 288 ms to print and a 20-qubit one would take about 18 s. Measured, not fixed; the .qc format has a quiet, QASM does not.

    
VQE and QAOA
The VQE (3 layers, BFGS, 56 gradients) takes 0.11 s; QAOA takes 0.12 to 1.0 s for 1 to 4 layers, 5.6 to 11.8 times faster than scipy’s BFGS on an unoptimised numpy version of the same circuit. SPSA runs take 2 to 4 s because each of their 1,600 to 2,400 evaluations starts a program (about 1.4 ms).

    
SPSA against Qiskit’s
opt’s SPSA takes 1.5 to 2.2 ms for 1,000 iterations on a built-in objective, 29 to 38 times less than Qiskit’s in Python, which says nothing about an objective that is a program (cancho-opt design, section 11).

  

  
Not measured: arm64 hardware (the aarch64 runs are emulation), a second reference such as Cirq, anything above 20 qubits, and whether an agent writes better quantum code with these refusals than without. Timings in m1-results.md are single runs on one machine.






  
Variational algorithms

  
A VQE for the ground state of a 4-qubit transverse-field Ising chain, written in cancho on this simulator, with cancho-opt’s opt minimize (Nelder-Mead and BFGS checked against scipy, SPSA against Qiskit’s) as the optimiser. These numbers are typed from examples/vqe/README.md, not rebuilt by this page; scripts/check_vqe.py checks the example against numpy and scipy.

  

    
Exact energy, exact gradient
BFGS with the parameter-shift gradient reaches the exact ground state energy, −4.7587704831, to 1e-9 in 56 gradients (3 layers, 16 angles). One run of Nelder-Mead stops short in 12 or more dimensions and has to be restarted.

    
With shots
Estimated from 1,000 shots per basis, the median error of the angles found (their exact energy against the ground state) is 0.063 for BFGS, 0.160 for Nelder-Mead and 0.056 for SPSA, which spends 2.5 times fewer shots than BFGS. At 100 shots SPSA gives 0.12 against BFGS’s 0.33.

    
The reported energy lies
With shot noise the optimiser’s own energy can be below the ground state (0.24 below, Nelder-Mead at 100 shots), which no exact energy can be. A read-out error pushes it the other way (+0.3) unless it is mitigated; mitigation changes the number quoted, not where the optimum is.

    
QAOA for MaxCut
The same optimiser on a second problem: MaxCut on a six-vertex prism, best cut 7 of 9 edges. With the exact gradient the ratio rises with every layer, 0.849, 0.943, 0.983, 0.999 for 1 to 4, to scipy’s optimum. From 100 shots per evaluation SPSA gets within 0.002 of the 2-layer optimum; Nelder-Mead stops at 0.91 with about four times the shots. Typed from examples/qaoa/README.md.

    
What SPSA does not do
With no noise at all, 800 iterations at the default gain stop 0.03 above the ground state where BFGS reaches 1e-9. That is the step gain, not a floor and not shot noise: a gain of 1 with a small probe gets 0.004, a gain of 3 diverges early. With shots a larger gain only helps from about 1,000 shots and 800 iterations, so the defaults stay. Five seeds, one ansatz, one machine.

  






  
On real devices

  
The simulator’s noise model, built from IBM’s published calibration, was compared with counts from two 156-qubit devices (ibm_fez, ibm_kingston) on the Open Plan, 26–27 October 2026. These numbers are typed from the files in docs/data/hardware/, not rebuilt by this page; the write-up is docs/hardware.md.

  

    
Where it matches
On ibm_kingston, away from a qubit stuck at 1, the model lands close to the device on mirror circuits: about 0.07–0.09 total-variation distance from the ideal for the model against 0.09–0.10 measured, about the same as Qiskit Aer’s own model.

    
Where it does not
On ibm_fez the calibration’s numbers moved more than the device did over 24 hours. The model changed from 0.31 to 0.16 when the calibration was republished; the device stayed between 0.23 and 0.34.

    
Drift it cannot see
ibm_kingston read 0.13–0.16 in an afternoon and evening, against 0.09–0.10 at other times, while the model stayed flat. A calibration taken once a day does not capture that.

    
A pre-run scan and fitted gate rates
The test written down in advance (issue 16) on ibm_fez: the two together cut the distance to 0.79 of the calibration’s, and 1 of 13 circuits was consistent with the model. Partly, bordering on a fail. 11 of the 13 circuits moved closer. ibm_kingston: the scan and the rates ran, the 13 circuits never did (the plan’s seconds ran out), so there is no result.

  

  
Not shown here: a second pass on ibm_kingston for issue 16, and anything beyond five qubits of a line. Two devices on one plan, two days of calibrations.






  
Try it

  
You need a Rust toolchain (to build the compiler) and Python 3. The compiler revision matters: rule tags can change between revisions.


git clone https://github.com/alpibrusl/cancho.git && git -C cancho checkout 3fa3fbb
(cd cancho && cargo build -p cancho)
git clone https://github.com/alpibrusl/cancho-quantum.git && cd cancho-quantum
export CANCHO=../cancho/target/debug/cancho
$CANCHO build src/*.cho --std -o qsim
printf 'n 2\nh 0\ncx 0 1\n' | ./qsim                       # a Bell state
printf 'dm 2\nh 0\ncx 0 1\ndepol 1 1 4\npurity\nquiet\n' | ./qsim   # exact noise: purity 0.5833...
./qsim < tests/qasm/qft4.qasm | head -3                   # OpenQASM in
python3 scripts/check_types.py
