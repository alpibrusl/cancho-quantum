Can a compiler refuse to clone a qubit?

A small quantum simulator written in cancho, built to find out what a language with linear types and capabilities catches in quantum code, and to say plainly what it does not.

What was tried, and what came out

  
The idea: qubits are linear resources. The test: write the simulator, then try to write the mistakes, and see which ones the checker stops.

  

    
No-cloning is a type error
A Qubit is a res: it cannot be copied, cannot be dropped, and only measure ends it. Cloning, dropping, measuring twice and escaping a borrow are all refused by rules cancho already had. No compiler change was made.

    
Reproducible to the byte
25 circuits, each run six ways (interpreted and compiled; Cranelift and LLVM; aarch64 under emulation). The outputs are identical, and their hashes are checked in.

    
A gap, stated up front
CNOT with one qubit as both control and target is not refused at check time: it is accepted, and stops at run time. The page lists this, and what would close it, in the gallery.

  






  
For humans

  
What this is, what you can do with it today, and how far to trust it.

  

    
What you can do

      
    
        
  • Run a circuit: write a few lines (h 0, cx 0 1, rz 2 1 4, m 1) and read the amplitudes.
    • 
        
  • Write a typed program with Qubit values and see the checker say no when you clone one.
    • 
        
  • Check the numbers yourself against Qiskit, and the bytes against the checked-in hashes.
    • 
      

    
How far to trust it

      
    
        
  • Amplitudes match Qiskit 2.6.1 to 1.221e-15 on 25 circuits (the gate is 1e-12). Up to 20 qubits.
    • 
        
  • It is a research prototype: one reference implementation, one compiler revision, one machine plus emulation.
    • 
        
  • It is not fast and not a rival to Qiskit Aer or qsim, and does not try to be.
    • 
      

  

  
The input is plain text, one operation per line, so a circuit can be hashed and kept beside its reference output:


n 2        # two qubits
h 0        # Hadamard on qubit 0
cx 0 1     # CNOT, control 0, target 1
m 0        # measure qubit 0 (seeded, deterministic)






  
For agents

  
Everything an agent needs is checked, tagged or hashed. No key, no model, no network after the clone.

What not to get wrong

      
    
        
  • Do not fix a refusal by copying a qubit. It cannot be copied; qubit.measure ends it.
    • 
        
  • CNOT on one qubit twice compiles. It is a known gap, not a bug in your setup; do not report it as a refusal.
    • 
        
  • Qubit { ... } can be written by hand from any module. That is a known gap too.
    • 
        
  • Do not edit tests/golden/ to make a check pass.
    • 
        
  • The aarch64 result is emulation, not hardware.
    •

Ask your coding agent to try it

  
Paste this into Claude Code, Codex or any agent that can run commands. It builds the compiler at the measured revision, runs the checks, and has the agent watch a clone get refused.

  

    
prompt raw

    
Install cancho-quantum and try it on one small circuit. Work in a new empty directory, keep every path free of spaces, and never use sudo. Run steps 2 to 5 in one shell session. Report honestly; do not retry a failing command in a loop and do not edit the repository to make a command pass.

1. Check that `git`, `cargo` (Rust, via rustup), `python3` and a C linker (`cc`) exist. If one is missing, stop and tell me which; do not install system packages on your own.

2. Get the cancho compiler at the revision this project was measured against, and build it:
   git clone https://github.com/alpibrusl/cancho.git
   git -C cancho checkout 3fa3fbb
   (cd cancho && cargo build -p cancho)
   export CANCHO="$PWD/cancho/target/debug/cancho"

3. Get the simulator:
   git clone https://github.com/alpibrusl/cancho-quantum.git
   cd cancho-quantum

4. Run the checks that need no network after the clone:
   python3 scripts/check_types.py          # every line must say ok; ends "16 of 16 fixtures behave as stated"
   Then, only if you may install Python packages into a virtual environment (python3 -m venv .venv && . .venv/bin/activate && pip install qiskit numpy):
   python3 scripts/check_diff.py           # amplitudes against Qiskit; ends with the worst error, which must be under 1e-12
   python3 scripts/check_determinism.py    # six builds per circuit must give identical bytes (omit --arm64 unless qemu-aarch64 is installed)

5. Try the simulator and the checker on your own input:
   $CANCHO build src/*.cho --std -o qsim
   printf 'n 2\nh 0\ncx 0 1\n' | ./qsim     # a Bell state: amp 0 and amp 3 are 7.071067811865475e-1
   Now make a program that clones a qubit and watch it be refused. Copy tests/reject/clone_qubit.cho, read it, and run:
   $CANCHO check src/complex.cho src/state.cho src/gates.cho src/measure.cho src/qubit.cho tests/reject/clone_qubit.cho --std ; echo "exit $?"           # expect exit 1
   $CANCHO check src/complex.cho src/state.cho src/gates.cho src/measure.cho src/qubit.cho tests/reject/clone_qubit.cho --std --output json          # the rule is "linear-use-after-move"
   Do not fix the refusal by copying the qubit: it cannot be copied. A qubit is ended by `qubit.measure`.
   Then run tests/accept/same_handle_cx.cho (see its header) and report what happened: it compiles and then stops at run time. That is a known gap, not a bug in your setup.

6. Tell me, briefly:
   - the exit code and the first line each command printed in step 5;
   - whether step 4's checks passed, and the last line each printed;
   - anything that failed, with the exact error.
Docs: README.md (the commands), docs/qubit-types.md (the design and what the checker cannot say), docs/m2-results.md (what was refused and what was not), docs/m3-results.md (determinism).

Refused: mistakes the checker catches

  
Each is a real fixture; the red line is the compiler's own message and the tag under the title is the rule.


    
  
  • No cloning
    
      
    Measuring the same qubit twice. The first measure consumes it.
    linear-use-after-move
    
      
    `q` has already been consumed; a `res` value is used exactly once
    
      
    Fixture
    

    • 
  
  • No dropping
    
      
    A gate borrows the qubit and hands it back, so the function still owes a consumption.
    linear-value-unconsumed
    
      
    `q` is still live here; a `res` value must be consumed on every path
    
      
    Fixture
    

    • 
  
  • Measurement collapses
    
      
    After measure there is no qubit left to borrow.
    linear-use-after-move
    
      
    `q` has already been consumed; there is nothing left to borrow
    
      
    Fixture
    

    • 
  
  • No escaping a borrow
    
      
    A reference to a qubit may not outlive the block that borrowed it.
    reference-escapes-region
    
      
    this returns a reference into `r`, which is a `borrow` block in this function; a reference may not outlive its region
    
      
    Fixture
    

    • 
  
  • One measurement per qubit
    
      
    measure inside a loop consumes on the first pass and has nothing on the second.
    linear-value-unconsumed
    
      
    `q` is consumed inside this loop; the next iteration would use it again
    
      
    Fixture
    

    • 
  
  • One gate at a time
    
      
    No second unique borrow of a qubit while a gate on it is in flight.
    borrow-conflict
    
      
    `q` is already uniquely borrowed; a `&!` reference is the only way to reach a value, so there is at most one
    
      
    Fixture
    

    • 
  
  • No peeking at identity
    
      
    The index of an owned qubit cannot be read out of it.
    linear-value-taken-apart
    
      
    `Qubit` is `res`, so a field cannot be read out of it; take the whole value apart with a destructuring `let` (a non-owning read is a borrow, which is §5)
    
      
    Fixture
    

    • 
  
  • Control is read, target is written
    
      
    A control borrowed shared cannot stand where the operand to change is expected.
    type-mismatch
    
      
    expected a unique reference `&!`, found a shared one `&`
    
      
    Fixture
    

    • 


  
Accepted, and should not be

  
Pinned as passing fixtures so that the day a rule refuses them, the build goes red.


    
  
  • CNOT with one qubit as both operands
    
      
    Accepted by the checker (compiles: yes), because a unique borrow is a copyable pointer. It stops at run time instead, with a trap (signal 4, SIGILL, on Linux). Two more ways to the same program are pinned the same way: a copied handle, and two qubits with the same index.
    
      
    Fixture Why
    

    • 
  
  • Forging a qubit
    
      
    A pub res struct can be built and taken apart from any module, so “only fresh makes qubits” is a convention. The page does not hide this: it is a request to the compiler, not a flaw of the simulator.
    
      
    Fixture

Planned

  
Not built, and not promised for any date. Each tile says what is missing.


    
  
  • A Qpu capability Needs the compiler
    
      
    Which backend a program can reach and how many shots it may spend, readable from the program text before it runs. Needs compiler work; shot budgets are only decidable for constant counts, so the honest claim is a declared bound a supervisor enforces.
    
      
    Plan
    

    • 
  
  • Refuse CNOT(q, q) at check time Needs the compiler
    
      
    A same-place-twice rule would close at least one of the three ways; its design predicts a second, which is not measured, and says the third needs a different fix. Written, not built.
    
      
    Design Asker
    

    • 
  
  • Private constructors Needs the compiler
    
      
    So that only the simulator can mint a qubit. A proposed opt-in opaque struct; written, not built.
    
      
    Design Asker
    

    • 
  
  • OpenQASM in and out Planned
    
      
    Emit first, parse later. The circuit format today is a stand-in.
    

    • 
  
  • A second reference, Cirq Planned
    
      
    Qiskit is the only reference so far. A second one would catch a convention both share.
    

    • 
  
  • Real arm64 hardware Planned
    
      
    The aarch64 result is emulation. A run on a real arm64 machine is still owed.
    
      
    Results
    

    • 
  
  • A cloud quantum service Later
    
      
    Submit a circuit over HTTPS. The authority report will be coarser here, because host-set bounds are design-only in cancho.
    

    • 
  
  • Adjoint and controlled gates Not possible yet
    
      
    Not possible today: cancho has no function values, so a gate cannot be passed to a transform. Circuits stay data.
    

    • 
  
  • A GPU backend Out of scope
    
      
    Out of scope until cancho-gpu exists. A state vector of 20 qubits is fine on one CPU core.
